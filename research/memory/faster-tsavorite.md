# FASTER, FasterLog, Tsavorite and Garnet: epochs, logs, sessions and a custom .NET TCP host

Research notes, 2026-10-06. Scope: the high-performance techniques of Microsoft Research's FASTER key-value store and its FasterLog, of their successors Tsavorite and TsavoriteLog inside Garnet, and of Garnet's own TCP host, read for what they imply for the GRPC.NET call interface draft ([CALL-INTERFACE.md](../../CALL-INTERFACE.md)) and the recommendations in [RESEARCH-MEMORY.md](../../RESEARCH-MEMORY.md).

[arenas-zero-alloc.md](arenas-zero-alloc.md) already has two short paragraphs on this family: "Pattern C" (Garnet's buffer pool and per-session scratch arenas) and "Pattern D" (FASTER's sector-aligned pool and epoch-protected pages). This note does not repeat them. It goes into how epochs, the hybrid log, the hash index, sessions, the log's tail reservation and commit, the device layer and Garnet's network host actually work, with the costs each one carries.

Every factual claim carries a source: a GitHub link pinned to a commit with line numbers, a documentation page, or a paper section. Statements marked **Inference** are the author's reading of that evidence, not something a source states.

## 0. Baseline: how JSON-RPC.NET batches socket writes

CALL-INTERFACE.md's "batched writes" note refers to this behaviour.

- **Synchronous methods.** The Kestrel connection handler reads whatever the transport has, cuts out every complete document with `JsonFramer.TryReadDocument`, runs each one straight into the connection's `PipeWriter`, and calls `FlushAsync` once after the loop, only if something was written ([JsonRpcConnectionHandler.cs#L75-L120](https://github.com/Astn/JSON-RPC.NET/blob/a87c6b9bc0431e74c9d59b82e1835d8e84a0cce6/AustinHarris.JsonRpc.AspNetCore/JsonRpcConnectionHandler.cs#L75-L120), flush at L103-L106).
- **Async methods.** Each reply is staged in a pooled, rewindable writer and copied to the pipe when its method completes. If the next method goes asynchronous while replies are already buffered, the handler flushes them first so they do not wait behind the slow call; otherwise it flushes once per read group ([JsonRpcConnectionHandler.Async.cs#L12-L80](https://github.com/Astn/JSON-RPC.NET/blob/a87c6b9bc0431e74c9d59b82e1835d8e84a0cce6/AustinHarris.JsonRpc.AspNetCore/JsonRpcConnectionHandler.Async.cs#L12-L80), early flush at L48-L58, final flush at L79).
- **The gRPC comparison client** mimics the same rule with `BufferHint` on every message but the last ([GrpcCompare.cs#L35-L36](https://github.com/Astn/JSON-RPC.NET/blob/a87c6b9bc0431e74c9d59b82e1835d8e84a0cce6/TestServer_Console/GrpcCompare.cs#L35-L36), [L165-L169](https://github.com/Astn/JSON-RPC.NET/blob/a87c6b9bc0431e74c9d59b82e1835d8e84a0cce6/TestServer_Console/GrpcCompare.cs#L165-L169)).

One connection is served by one loop, so there is never more than one writer per pipe. §8 shows Garnet does the same thing with a different buffer model.

## 1. Epoch protection (`LightEpoch`)

### 1.1 The model, as published

- **Counters.** A shared current epoch *E*; a thread-local copy *E<sub>T</sub>* per thread, kept in a shared epoch table "with one cache-line per thread"; a safe epoch *E<sub>s</sub>*, the largest epoch every thread has passed. *E<sub>s</sub>* is computed by scanning the table ([FASTER paper §2.3](https://www.microsoft.com/en-us/research/uploads/prod/2018/03/faster-sigmod18.pdf)).
- **Trigger actions.** Bumping *E* from *c* to *c+1* can register an action that runs once epoch *c* is safe. Actions sit in a small array, the drain list, and compare-and-swap makes each one run exactly once (§2.3).
- **Four operations.** Acquire, Refresh, BumpEpoch(action), Release (§2.4). A FASTER thread refreshes "e.g., every 256 operations" and calls `CompletePending` every 64K operations (§2.5).
- **What it is used for in FASTER.** Garbage collection, index resizing, circular-buffer maintenance and page flushing, log page boundaries and checkpointing (§2.4).
- **What it replaces.** The paper contrasts it with pinning pages in a buffer pool by latch before every access (§5.2) and with holding a read lock on the read-only offset (§6.2). EPVS states the cost being avoided: a shared latch writes a shared counter and causes cache-line ping-pong, whereas a refresh reads the global epoch and writes only the thread's own entry ([EPVS §2](https://badrish.net/papers/epvs-damon2022.pdf)).
- **Garnet's generalization.** The epoch-protected state machine (EPSM) runs control-plane phases (index growth, checkpoints, page flush and eviction, migration) and bumps the epoch at each phase change. Garnet drives EPSM from a background task "so that application threads do not need to perform the actual EPSM actions" ([Garnet paper §3.3](https://www.vldb.org/pvldb/vol19/p224-chandramouli.pdf)).

### 1.2 The Tsavorite implementation

- **Per-thread table.** `kTableSize = max(128, 2 × ProcessorCount)` entries ([LightEpoch.cs#L100](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L100)). The table is a pinned array (`GC.AllocateArray<Entry>(kTableSize + 2, true)`) whose pointer is rounded up to a 64-byte boundary ([L181-L201](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L181-L201)).
- **Cache-line entry.** `Entry` is an explicit 64-byte struct: `localCurrentEpoch` at offset 0, `threadId` at 8, and six general-purpose per-thread "user words" at 16 to 56 ([L844-L882](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L844-L882); `MaxUserWords = 6`, [L161](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L161)).
- **Thread-static index.** Each thread keeps its managed thread id, two Murmur3-derived probe offsets, and an inline array of 1,024 `int`s that maps a `LightEpoch` instance id to that thread's table slot. The comment says this gives `ThreadLocal<T>` semantics without its overhead ([L52-L85](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L52-L85)). At most 1,024 instances may exist per process ([L30](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L30), [L203-L213](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L203-L213)).
- **Enter (`Resume` → `Acquire`).** Claim a table slot by CAS on its `threadId` (primary offset, then the alternate, then two linear passes round the table), copy `CurrentEpoch` into `localCurrentEpoch`, and run the drain list if it is non-empty ([L515-L537](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L515-L537), [L568-L615](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L568-L615), [L674-L684](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L674-L684)).
- **Leave (`Suspend` → `Release`).** Zero `localCurrentEpoch` and `threadId`, forget the slot, and wake one waiter if any are queued. If drain actions are pending and this was the last protected thread, it drains them itself ([L333-L338](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L333-L338), [L543-L557](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L543-L557), [L461-L477](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L461-L477)).
- **Refresh (`ProtectAndDrain`).** Re-copy `CurrentEpoch` into the slot, drain if needed, and briefly suspend and resume if other threads are waiting for a slot ([L298-L317](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L298-L317)).
- **Deferred actions.** The drain list is a fixed array of 16 `(epoch, Action)` pairs ([L105](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L105), [L138-L139](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L138-L139)). `BumpCurrentEpoch(Action)` increments `CurrentEpoch` and CAS-claims a free slot for the action tagged with the prior epoch. If it finds a slot whose action is already safe, it runs that action and reuses the slot. If all 16 are busy it refreshes, yields and retries ([L384-L431](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L384-L431)).
- **Safe epoch.** `ComputeNewSafeToReclaimEpoch` scans every table entry for the minimum non-zero `localCurrentEpoch` and sets the safe epoch to one less ([L438-L455](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L438-L455)). `Drain` runs every action whose epoch is now safe, CAS-claiming each slot so it runs once, on whichever thread got there ([L484-L509](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L484-L509)).
- **Full table.** A thread that finds no free slot increments a waiter count and blocks on a `SemaphoreSlim` until a `Release` signals it ([L637-L667](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L637-L667)). The Garnet docs still describe the older behaviour of yielding until a slot frees ([epochprotection.md#L32](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/website/docs/dev/tsavorite/epochprotection.md?plain=1#L32)).
- **User words.** Subsystems can claim one of the six per-thread words, write it through `ThisThreadUserWord` while protected, and read the minimum across all threads with `GetMinUserWord`, a strided scan of one column of the table ([L746-L825](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L746-L825)). TsavoriteLog uses one to track in-flight appends (§6.2).

### 1.3 How FASTER's version differs

- FASTER keeps a second, static table shared by all `LightEpoch` instances and reference-counts a thread's slot across instances; a full table spins with `Thread.Yield` ([FS LightEpoch.cs#L20-L51](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/cs/src/core/Epochs/LightEpoch.cs#L20-L51), [L109-L125](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/cs/src/core/Epochs/LightEpoch.cs#L109-L125), [L419-L486](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/cs/src/core/Epochs/LightEpoch.cs#L419-L486)).
- Its entry has a `reentrant` field and six `markers` where Tsavorite has user words ([L524-L545](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/cs/src/core/Epochs/LightEpoch.cs#L524-L545)).

### 1.4 Costs

- **Published throughput.** The pull request that introduced FasterLog reports 35 million acquire/release pairs per second per thread, scaling linearly, and 100 million per second when the thread is pre-acquired ([microsoft/FASTER#177](https://github.com/microsoft/FASTER/pull/177), PR description). EPVS calls the framework able to sustain tens of millions of fine-grained operations per second ([EPVS §1](https://badrish.net/papers/epvs-damon2022.pdf)).
- **Common path.** Enter is one CAS on a slot no other thread normally touches plus a plain store; leave is two plain stores plus two reads of shared counters (`drainCount`, `waiterCount`). Neither scans the table while the drain list is empty (§1.2 lines).
- **Rare path.** A bump or a non-empty drain list scans the whole table: at least 128 cache lines, 8 KiB (§1.2).
- **Memory.** 64 bytes × (`kTableSize` + 2) pinned per instance, plus a 4 KiB thread-static array on every thread that touches any instance (1,024 × 4-byte ints, §1.2).
- **Discipline.** Re-entering an epoch from a callback or an `IDevice` implementation is a bug, and the debug assertions tell task users to set `TaskCreationOptions.RunContinuationsAsynchronously` ([L515-L537](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Epochs/LightEpoch.cs#L515-L537)). Slots are keyed by thread (§1.2), so protection belongs to an OS thread, not to a logical operation.
- **Engineering cost.** The EPVS authors report that epoch-based latch-free code in FASTER and Silo took "months of careful design" ([EPVS §1](https://badrish.net/papers/epvs-damon2022.pdf)), and that a checkpoint rebuilt on EPVS took a few hours but lost to the hand-written one when protected regions were coarse (§6.1).

**Inference:** an epoch is cheap only when protected regions are short and synchronous. A thread that stays protected across a blocking wait or a slow call holds back the safe epoch for every other thread and every pending reclamation. A protected region cannot span an `await`, because the continuation may resume on another thread that does not own the slot.

## 2. The HybridLog

### 2.1 Regions and addresses

- **Paper.** A logical address space spans memory and storage. The in-memory tail is a circular buffer of sector-aligned page frames, so I/O needs no extra copy ([FASTER paper §5.1](https://www.microsoft.com/en-us/research/uploads/prod/2018/03/faster-sigmod18.pdf)). Records above the read-only offset are updated in place; records between the head and the read-only offset are updated by read-copy-update to the tail; records below the head are fetched from storage asynchronously first (§6.1, Table 1).
- **Fuzzy region.** Threads act on locally cached offsets, so a safe read-only offset trails the read-only offset by one epoch. In the region between them a blind update may append, a read-modify-write goes pending to avoid the lost-update anomaly, and a CRDT update may append a delta (§6.2–6.3, Table 2). With threads refreshing every 256 operations, under 3% of updates fell in the fuzzy region on 56 threads (§7.4.3).
- **Sizing.** A 90:10 split between mutable and read-only memory performed well (§6.4). Tsavorite defaults `MutableFraction` to 0.9 ([KVSettings.cs#L65](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Common/KVSettings.cs#L65)) and snaps the computed read-only address to a page boundary ([AllocatorBase.cs#L1290-L1326](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L1290-L1326)).
- **Tsavorite's address set.** `BeginAddress`, `HeadAddress`, `SafeHeadAddress`, `ClosedUntilAddress`, `FlushedUntilAddress`, `SafeReadOnlyAddress` and `ReadOnlyAddress`, each with a comment on which thread may move it and what holding the epoch guarantees about it ([AllocatorBase.cs#L105-L137](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L105-L137)).
- **Garnet's locking.** In Tsavorite only structure changes are latch-free; reads and in-place updates of a record still take a shared or exclusive bucket latch ([Garnet paper §4.5](https://www.vldb.org/pvldb/vol19/p224-chandramouli.pdf)).

### 2.2 Allocating at the tail

- **One word for page and offset.** `PageOffset` overlays an `int Offset` and an `int Page` on one `long` ([PageUnit.cs#L32-L41](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/PageUnit.cs#L32-L41)), stored in `TailPageOffset` ([AllocatorBase.cs#L191](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L191)). The paper describes the same design (§5.1).
- **Fast path.** `TryAllocate` does `Interlocked.Add(ref TailPageOffset.PageAndOffset, numSlots)`. If the new offset still fits the page, the slot is the old offset ([AllocatorBase.cs#L1207-L1240](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L1207-L1240)).
- **Page turn.** The one thread whose add crossed the page end owns the turn. It checks that the next frame is flushed and closed, issues address shifts, allocates the next pages if needed, and publishes the new tail; every other thread that overflowed returns "retry now" or "retry later" ([HandlePageOverflow, L1133-L1201](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L1133-L1201); flush and close checks [L1105-L1130](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L1105-L1130)).
- **Waiting.** `TryAllocateRetryNow` polls device completions, refreshes the epoch and yields up to `kFlushSpinCount` (10) times, then suspends its epoch and waits up to 1 ms on a flush event ([L1247-L1280](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L1247-L1280); [Constants.cs#L47](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Tsavorite/Constants.cs#L47)). Its comment says this replaced 64 inserter threads spinning through a roughly 900 µs libaio flush.
- **Append-only cost.** With an append-only allocator the paper measured no more than 20 million operations per second, not scaling with threads, because of "contention on the tail" (§5, §7.4.1).

### 2.3 Pages: allocation, pinning, alignment and reuse

- **Frames.** The buffer holds `BufferSize` frames, the next power of two at or above the maximum page count ([AllocatorBase.cs#L631](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L631)). Each page is a pinned array of `PageSize + 2 × sectorSize` bytes whose pointer is rounded up to the sector size ([L753-L760](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L753-L760)). The default page is 32 MiB ([KVSettings.cs#L37](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Common/KVSettings.cs#L37)).
- **Reuse.** Pages are allocated lazily into a frame; when memory is size-tracked, a freed page goes to a free-page pool and the next allocation takes from it before allocating ([SpanByteAllocatorImpl.cs#L37-L78](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/SpanByteAllocatorImpl.cs#L37-L78)).

### 2.4 Shifting the read-only and head addresses through epochs

- **Read-only.** `ShiftReadOnlyAddress` moves `ReadOnlyAddress` monotonically and bumps the epoch with `OnPagesMarkedReadOnly` as the trigger ([AllocatorBase.cs#L1346-L1354](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L1346-L1354)). When the epoch is safe, the trigger advances `SafeReadOnlyAddress` and issues the asynchronous flush of the newly immutable range ([L1438-L1452](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L1438-L1452)).
- **Head.** `ShiftHeadAddress` caps the new head at `FlushedUntilAddress`, moves it, and bumps the epoch with `OnPagesClosed` ([L1556-L1574](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L1556-L1574)). `OnPagesClosed` advances `SafeHeadAddress` and lets a single worker loop close and evict the range ([L1455-L1529](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L1455-L1529)).
- **Flushed address.** Flush completions advance `FlushedUntilAddress` page by page as contiguous ranges finish ([L1580-L1626](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L1580-L1626)).
- **Why this works.** A page is flushed only after every thread has seen it as read-only, and evicted only after every thread has seen the new head, so no reader or writer can still hold a pointer into it (FASTER paper §5.2, §6.1).

## 3. The hash index

- **Buckets.** A cache-aligned array of 2<sup>k</sup> 64-byte buckets, each with seven 8-byte entries and one overflow pointer. Each entry has a 15-bit tag, a tentative bit and a 48-bit address, and the tag extends the hash resolution from *k* to *k*+15 bits ([FASTER paper §3.1](https://www.microsoft.com/en-us/research/uploads/prod/2018/03/faster-sigmod18.pdf), Fig. 2).
- **Tsavorite's layout.** `HashBucket` is eight `long`s in an explicit layout ([HashBucket.cs#L12-L34](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Tsavorite/HashBucket.cs#L12-L34)). Entry bits: tentative at bit 63, a 15-bit tag, a 48-bit address ([HashBucketEntry.cs#L18-L30](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Tsavorite/HashBucketEntry.cs#L18-L30), [LogAddress.cs#L14](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Common/LogAddress.cs#L14)).
- **Latch in the overflow word.** The eighth word also carries a 15-bit shared-latch count and a 1-bit exclusive latch, both taken by CAS ([HashBucket.cs#L16-L61](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Tsavorite/HashBucket.cs#L16-L61)). The Garnet paper says this puts the lock table on the cache line the lookup already loaded ([§4.4](https://www.vldb.org/pvldb/vol19/p224-chandramouli.pdf)).
- **Table memory.** A pinned array of buckets, over-allocated by one sector and aligned to the sector size ([TsavoriteBase.cs#L112-L127](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Tsavorite/TsavoriteBase.cs#L112-L127)).
- **Latch-free insert.**
  - Two threads choosing different empty slots for the same tag would break the one-entry-per-tag invariant, and deletes defeat a "first empty slot" rule (paper §3.2, Fig. 3a).
  - The fix is two phases: CAS the tag into a free slot with the tentative bit set (invisible to readers), rescan the bucket for another entry with the same tag, then either undo or clear the tentative bit (§3.2, Fig. 3b).
  - Tsavorite's `FindOrCreateTag` does exactly this ([TsavoriteBase.cs#L177-L218](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Tsavorite/TsavoriteBase.cs#L177-L218)).
- **Overflow buckets.** When a chain is full, a thread allocates an overflow bucket from a fixed-page allocator and CASes its address into the overflow word; the loser frees its allocation and follows the winner's bucket ([L270-L295](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Tsavorite/TsavoriteBase.cs#L270-L295); allocator field [L28](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Tsavorite/TsavoriteBase.cs#L28)).
- **Resizing.**
  - Paper: done with epochs and a state machine at low overhead, and the latch-free index allows a fuzzy checkpoint without read locks (§3.3).
  - Tsavorite: `PREPARE_GROW` is a full barrier on new transactions; `IN_PROGRESS_GROW` allocates a table twice the size, swaps in a fresh overflow allocator, and splits old buckets in chunks of 16,384 ([IndexResizeSMTask.cs#L24-L78](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Checkpointing/IndexResizeSMTask.cs#L24-L78); [Constants.cs#L54-L55](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Tsavorite/Constants.cs#L54-L55)).
  - Operations that touch a bucket during the grow split it on demand ([ContainsKeyInMemory.cs#L23-L24](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Tsavorite/Implementation/ContainsKeyInMemory.cs#L23-L24)), while a background pass splits the rest.

Garnet's string-store callbacks are a `readonly partial struct MainSessionFunctions` ([MainSessionFunctions.cs#L12](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Storage/Functions/MainStore/MainSessionFunctions.cs#L12)).
- **Why structs.** The Tsavorite docs state that type parameters implemented by classes do not get inlined code, because the JIT shares one body for all reference types, while each struct gets its own specialized body ([storefunctions.md#L21](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/website/docs/dev/tsavorite/storefunctions.md?plain=1#L21), [L33](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/website/docs/dev/tsavorite/storefunctions.md?plain=1#L33)).

The FASTER docs later recommend passing a `struct` scan-functions implementation by reference so that it inlines ([fasterkv-basics.md#L427-L430](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/docs/_docs/20-fasterkv-basics.md?plain=1#L427-L430)).

### 4.2 Session-local state and the epoch per operation

- **Mono-threaded sessions.** A session is a sequence of operations with no concurrency inside it, not tied to a thread ([fasterkv-basics.md#L216](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/docs/_docs/20-fasterkv-basics.md?plain=1#L216)).
- **Epoch per call.** `BasicContext.Read` resumes the epoch, runs the operation and suspends it in a `finally` ([BasicContext.cs#L79-L90](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/ClientSession/BasicContext.cs#L79-L90)). `UnsafeContext` leaves epoch control to the caller ([UnsafeContext.cs#L12-L14](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/ClientSession/UnsafeContext.cs#L12-L14)); Garnet uses it to hold one epoch across a multi-key bitmap operation ([BitmapOps.cs#L101-L201](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Storage/Session/MainStore/BitmapOps.cs#L101-L201)).
- **Per-session pending state.** Each session's execution context holds a `Dictionary<long, PendingContext>` of in-flight I/O, an `AsyncQueue` of completed reads, an async countdown, and a stack of reusable heap containers ([ExecutionContext.cs#L27-L53](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Common/ExecutionContext.cs#L27-L53)).

### 4.3 Pending and async completion: what allocates, and when

- **In-memory hits allocate nothing extra.** `PendingContext` is a struct ([PendingContext.cs#L19](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Common/PendingContext.cs#L19)). Garnet's CI fails a benchmark whose allocated bytes exceed the expected value by more than 10% ([benchmarking/overview.md#L16](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/website/docs/benchmarking/overview.md?plain=1#L16)), and expects 0 bytes for GET, SET and INCR in the store-level benchmarks ([BDN_Benchmark_Config.json#L261-L290](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/test/BDNPerfTests/BDN_Benchmark_Config.json#L261-L290)).
- **Going pending copies the key and input.** They are copied into sector-aligned pooled memory held by a heap container. The container comes from the session's stack and is allocated only when the stack is empty, then returns itself on dispose ([PendingContext.cs#L152-L185](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Index/Common/PendingContext.cs#L152-L185); [SpanByteHeapContainer.cs#L21-L55](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/VarLen/SpanByteHeapContainer.cs#L21-L55)).
- **Delegate caching.** The disk-read callback delegate is cached in a field because the compiler does not cache method-group conversions for instance methods; without it every pending read would allocate a delegate of about 48 bytes. Disk-read result objects are pooled in a `ConcurrentQueue` ([AllocatorBase.cs#L214-L226](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L214-L226)).
- **Completion stays on the session.** The device callback enqueues the result on the issuing session's queue ([AllocatorBase.cs#L2186-L2273](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L2186-L2273), enqueue at L2249). The session thread finishes the operation when it calls `CompletePending`, as the paper describes (§5.3); the async form awaits the queue ([CompletePendingAsync.cs#L22-L46](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Async/CompletePendingAsync.cs#L22-L46)).
- **FASTER's async read.** `ReadAsync` returns a `ValueTask` wrapping a struct result when the read completes in memory, and calls an `async ValueTask` method only when it went pending ([FS Async/ReadAsync.cs#L105-L150](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/cs/src/core/Async/ReadAsync.cs#L105-L150)).

**Inference:** the slow path's `async ValueTask` method allocates its state machine on the heap only when it actually suspends, which happens only for I/O. That is the same synchronous-fast-path, async-slow-path split CALL-INTERFACE.md asks for.

## 5. Variable-length data stored inline

- **FASTER `SpanByte`.** A 4-byte length whose top two bits are flags, followed by an optional 8-byte metadata field and the payload. The payload is at most 1 GB. A serialized `SpanByte` holds its bytes inline; an unserialized one holds a pointer to pinned memory ([FS VarLen/SpanByte.cs#L12-L38](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/cs/src/core/VarLen/SpanByte.cs#L12-L38)). The docs call it the highest-performance variable-length option, usable only with pinned memory and fixed spans ([fasterkv-basics.md#L478](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/docs/_docs/20-fasterkv-basics.md?plain=1#L478)).
- **Tsavorite.**
  - `PinnedSpanByte` is just a pointer and a length over already-pinned memory, built from a pinned span or a length-prefixed pointer ([PinnedSpanByte.cs#L20-L46](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/VarLen/PinnedSpanByte.cs#L20-L46), [L144-L161](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/VarLen/PinnedSpanByte.cs#L144-L161)).
  - Spans serialize with a 4-byte length prefix ([VarLen/SpanByte.cs#L45-L105](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/VarLen/SpanByte.cs#L45-L105)).
  - The fixed-size blittable allocator has been removed, so keys are always byte spans ([logrecord.md#L31](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/website/docs/dev/tsavorite/logrecord.md?plain=1#L31)).
- **Record layout.** A 64-bit header holding the previous address, then key length and key bytes, then the value in the same form, with optional expiration and ETag fields ([Garnet paper §4.1](https://www.vldb.org/pvldb/vol19/p224-chandramouli.pdf), Fig. 3). Lengths use a variable number of bytes recorded in an indicator byte ([logrecord.md#L118-L133](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/website/docs/dev/tsavorite/logrecord.md?plain=1#L118-L133)).
- **When data leaves the log.** In the object store, oversized keys or values "overflow" into a separate `byte[]`, and heap objects are referenced by a 4-byte id into an `ObjectIdMap`, because .NET references cannot be stored in unmanaged pages ([logrecord.md#L48-L50](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/website/docs/dev/tsavorite/logrecord.md?plain=1#L48-L50), [L73-L75](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/website/docs/dev/tsavorite/logrecord.md?plain=1#L73-L75)). The paper describes an 8-byte pointer (§4.1); the docs at this commit describe the 4-byte id.

**Inference:** inline storage works because every key and value is opaque bytes with a length. A protobuf message has nested, optional and repeated fields, so the same layout fits GRPC.NET only for the raw message bytes themselves, which is what the 5-byte gRPC prefix already frames.

## 6. FasterLog and TsavoriteLog

### 6.1 Latch-free tail reservation

- **Enqueue.** `TryEnqueue(ReadOnlySpan<byte>)` enters the epoch, reserves `headerSize + Align(length)` bytes through the hybrid-log allocator's fetch-and-add (§2.2), copies the payload into the page, writes the length header, leaves the epoch, and commits only if auto-commit is on ([TsavoriteLog.cs#L966-L997](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLog.cs#L966-L997)). FASTER's version is the same ([FS FasterLog.cs#L649-L680](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/cs/src/core/FasterLog/FasterLog.cs#L649-L680)).
- **Many writers, one copy.** Every enqueuing thread copies its own bytes straight into its reserved slot in the shared page, in parallel; ordering is fixed by the order of the fetch-and-adds.
- **Variants.** There are batch enqueues that commit all or nothing ([fasterlog-basics.md#L50-L54](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/docs/_docs/40-fasterlog-basics.md?plain=1#L50-L54)), struct-header plus span overloads that write several pieces into one entry ([TsavoriteLog.cs#L1005-L1320](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLog.cs#L1005-L1320)), and `EnqueueAsync` that waits for space ([L1565-L1745](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLog.cs#L1565-L1745)).

### 6.2 The safe tail: knowing which reserved bytes are written

A reserved slot may not be filled yet when a reader or flusher looks at it.

- **Tsavorite's design.**
  - Before its fetch-and-add, each producer writes a lower bound of its slot address into its epoch-table user word, and clears it after the copy.
  - The safe tail is the minimum of the tail and every thread's published value, computed by one strided scan.
  - The comment says this replaced a background worker plus epoch bump and removed a tuning knob ([TsavoriteLog.cs#L260-L309](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLog.cs#L260-L309)).
  - The reader reads the tail first and then the in-flight column, with a full fence between, so it can never see a moved tail without the matching in-flight mark ([L382-L400](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLog.cs#L382-L400)).
  - The bound may lag the true value by a few entries per thread, which the comment judges negligible.
- **FASTER's older design.** It refreshes the safe tail from an epoch-protected runner triggered after enqueues ([FS FasterLog.cs#L135](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/cs/src/core/FasterLog/FasterLog.cs#L135), [L514](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/cs/src/core/FasterLog/FasterLog.cs#L514), [L1939-L1943](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/cs/src/core/FasterLog/FasterLog.cs#L1939-L1943)).

### 6.3 Commit, group commit and waiting

- **Commit.** `CommitInternal` asks the commit policy for admission, then under a lock assigns the next commit number, records the current tail as the commit point, and queues the request. It then moves the read-only address to the tail inside the epoch, which flushes everything up to there through the §2.4 machinery ([TsavoriteLog.cs#L3231-L3326](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLog.cs#L3231-L3326)).
- **Group commit by construction.** One commit covers every enqueue below the tail it recorded. The docs suggest committing "as frequently as you need, e.g., every 5ms" and keeping commit separate from enqueue to get group commit ([fasterlog-basics.md#L18-L19](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/docs/_docs/40-fasterlog-basics.md?plain=1#L18-L19), [L95-L100](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/docs/_docs/40-fasterlog-basics.md?plain=1#L95-L100)).
- **Policies.** `Default`, `MaxParallel(k)`, which limits concurrent commits, and `RateLimit(ms, bytes)`, which admits a commit only past a time or size threshold ([LogCommitPolicy.cs#L11-L76](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/LogCommitPolicy.cs#L11-L76)).
- **Completion.** Flush completions call `CommitCallback`, which hands work to a serial LIFO work queue ([L2577-L2582](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLog.cs#L2577-L2582), [L226](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLog.cs#L226)). The worker writes commit metadata, runs callbacks, swaps in a fresh `TaskCompletionSource<LinkedCommitInfo>` and completes the old one with a struct pointing at the new task ([L2738-L2748](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLog.cs#L2738-L2748); field [L41](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLog.cs#L41); struct [CommitInfo.cs#L34](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/CommitInfo.cs#L34)).
- **Waiting.**
  - `WaitForCommitAsync` walks that chain of tasks until the commit covers its address ([L1769-L1782](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLog.cs#L1769-L1782)).
  - Synchronous `WaitForCommit` spins with `Thread.Yield` ([L1748-L1757](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLog.cs#L1748-L1757)).
  - Readers waiting for uncommitted data share one lazily created TCS, installed by CAS ([L1788-L1826](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLog.cs#L1788-L1826)).
  - So the allocation is one TCS per commit, shared by every waiter, not one per enqueue.
- **Garnet's append-only file.**
  - `CommitFrequencyMs` = 0 commits per operation, −1 leaves commits to an explicit command, and a positive value runs a background loop that commits and then sleeps ([GarnetServerOptions.cs#L92-L100](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Servers/GarnetServerOptions.cs#L92-L100); [StoreWrapper.cs#L642-L663](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/StoreWrapper.cs#L642-L663)).
  - With `WaitForCommit` on, which its comment warns will greatly increase latency ([L125-L127](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Servers/GarnetServerOptions.cs#L125-L127)), any batch containing a write blocks the network thread before sending until the log commit covers it ([RespServerSession.cs#L1410-L1434](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Resp/RespServerSession.cs#L1410-L1434); [RespCommand.cs#L2960-L2982](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Resp/Parser/RespCommand.cs#L2960-L2982)).
  - So one wait covers a whole pipelined batch: group commit and send batching line up.

### 6.4 Scan iterators: copy or zero-copy

- **Copying.** `GetNext(out byte[] …)` allocates a new array per entry unless the caller supplied an allocation delegate ([TsavoriteLogScanIterator.cs#L221-L295](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLogScanIterator.cs#L221-L295), `new byte[]` at L282). `GetNext(MemoryPool<byte> …)` rents instead ([L366](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLogScanIterator.cs#L366)).
- **Zero-copy.** `TryConsumeNext<T>(T consumer) where T : ILogEntryConsumer` hands a pointer and length into the log page to the consumer under epoch protection ([L381](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLogScanIterator.cs#L381); [ILogEntryConsumer.cs#L9-L20](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/ILogEntryConsumer.cs#L9-L20)). `UnsafeGetNext` returns a raw pointer and keeps the epoch held until `UnsafeRelease`, documented as for advanced users only ([L549-L617](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/TsavoriteLog/TsavoriteLogScanIterator.cs#L549-L617)).
- **Visibility.** By default iterators see only committed entries; `scanUncommitted` lets them read up to the safe tail, like a channel ([fasterlog-basics.md#L160-L175](https://github.com/microsoft/FASTER/blob/332ea7da532a688acf648ee60c4f63a1caeaf1f7/docs/_docs/40-fasterlog-basics.md?plain=1#L160-L175)).

### 6.5 Published FasterLog figures

- **Bandwidth.** With 100-byte payloads, about 1 GB/s to a modern NVMe SSD from one thread, "with log tail increment being the bottleneck" as append threads increase. With 1,000-byte payloads, 1.8–2 GB/s from one thread, close to the SSD's limit ([microsoft/FASTER#177, comment of 2019-09-19](https://github.com/microsoft/FASTER/pull/177#issuecomment-532973235)). No machine details are given beyond that.
- **Tail contention elsewhere.** In CPR's evaluation, contention on the tail of a write-ahead log was a scalability bottleneck, costing about 30–40% with 10-key transactions on 64 threads ([CPR §7.2.1](https://www.microsoft.com/en-us/research/uploads/prod/2019/01/cpr-sigmod19.pdf)).

## 7. Device and I/O

- **`IDevice`.** Sector size, segment size, `WriteAsync` and `ReadAsync` taking a raw pointer, an address, a length, a callback `(uint errorCode, uint numBytes, object context)` and a context object, plus `TryComplete` to poll completions and `Throttle` ([IDevice.cs#L14-L144](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Device/IDevice.cs#L14-L144)). The model is callbacks, not tasks.
- **Sector alignment.** Pages and I/O buffers are sector-aligned so the device can do unbuffered I/O (FASTER paper §5.1; §2.3 above). The allocator refuses a device whose sector size does not divide its own ([AllocatorBase.cs#L488-L491](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L488-L491)).
- **Buffer pool.** `SectorAlignedBufferPool` is described in [arenas-zero-alloc.md](arenas-zero-alloc.md) Pattern D. At this commit it has 32 levels of `ConcurrentQueue`, pinned aligned arrays, and clears buffers on return ([BufferPool.cs#L250-L430](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Utilities/BufferPool.cs#L250-L430); allocation [L153-L156](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Utilities/BufferPool.cs#L153-L156)).
- **Windows.** `LocalStorageDevice` either creates its own I/O completion port with dedicated background completion threads, or binds the file to the thread pool. Its `TryComplete` dequeues up to 8 completions at a time with `GetQueuedCompletionStatusEx` on the caller's thread ([LocalStorageDevice.cs#L129-L145](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Device/LocalStorageDevice.cs#L129-L145), [L393-L415](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Device/LocalStorageDevice.cs#L393-L415), [L474-L480](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Device/LocalStorageDevice.cs#L474-L480)). `Overlapped` structures are pooled in a queue rather than allocated per I/O ([L227-L239](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Device/LocalStorageDevice.cs#L227-L239)).
- **Cooperative completion.** The log allocator calls `TryComplete` from its allocation retry loop, so a thread waiting for space also processes I/O completions ([AllocatorBase.cs#L1258](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Allocator/AllocatorBase.cs#L1258)).
- **Linux.** `NativeStorageDevice` loads a native library built against io_uring and libaio, falling back to a libaio-only build ([NativeStorageDevice.cs#L105-L160](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/storage/Tsavorite/cs/src/core/Device/NativeStorageDevice.cs#L105-L160)). The Garnet paper reports io_uring with 8 completion threads saturating a measured 32.5 GB/s eight-SSD RAID during a checkpoint ([§8.6](https://www.vldb.org/pvldb/vol19/p224-chandramouli.pdf)).

## 8. Garnet's network layer: a custom .NET TCP host without ASP.NET Core

### 8.1 Accepting connections

- **Listener.** `GarnetServerTcp` owns a raw `Socket` with `ReuseAddress` set, binds and listens with a backlog of 512, and accepts with one reusable `SocketAsyncEventArgs` in a loop of the form `do { … } while (!AcceptAsync(e))`, so synchronous completions are handled inline ([GarnetServerTcp.cs#L70-L111](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Servers/GarnetServerTcp.cs#L70-L111), [L139-L172](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Servers/GarnetServerTcp.cs#L139-L172)).
- **Errors.** Accept errors fall into three tiers: stop, back off with `Thread.Sleep` on the accepting thread, or continue ([L174-L217](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Servers/GarnetServerTcp.cs#L174-L217)).
- **Per connection.** It enforces an optional connection limit, sets `NoDelay` on TCP sockets, creates a handler, registers it and starts it ([L219-L304](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Servers/GarnetServerTcp.cs#L219-L304)). The docs describe the same flow ([network.md#L12-L15](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/website/docs/dev/network.md?plain=1#L12-L15)).

### 8.2 Receive and send buffers

- **Sizes.** The server buffer size is the larger of 128 KiB (`MaxBatchSize = 1 << 17`) and twice the maximum output size plus a header ([BufferSizeUtils.cs#L12](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/BufferSizeUtils.cs#L12), [L35-L43](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/BufferSizeUtils.cs#L35-L43)). Default maximum sizes are 4,096 bytes ([MaxSizeSettings.cs#L14-L29](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/MaxSizeSettings.cs#L14-L29)), so both send and initial receive buffers are 128 KiB, with a 1 MiB receive ceiling by default ([NetworkBufferSettings.cs#L38-L51](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/NetworkBufferSettings.cs#L38-L51); constructed at [GarnetServerTcp.cs#L84-L86](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Servers/GarnetServerTcp.cs#L84-L86)).
- **Pooling and pinning.** All network buffers come from one server-wide `LimitedFixedBufferPool` with power-of-two levels of 16 entries each ([NetworkBufferSettings.cs#L79-L88](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/NetworkBufferSettings.cs#L79-L88)). Each `PoolEntry` is a pinned-heap array with a cached raw pointer ([PoolEntry.cs#L42-L43](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Memory/PoolEntry.cs#L42-L43)). Returned buffers are zeroed with `Array.Clear` before re-queueing ([LimitedFixedBufferPool.cs#L107-L127](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Memory/LimitedFixedBufferPool.cs#L107-L127)).
- **Receive buffer.** One per connection, taken from the pool when the handler is built ([TcpNetworkHandlerBase.cs#L269-L274](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/TcpNetworkHandlerBase.cs#L269-L274)). After each processing pass, unconsumed bytes are moved to the front with `Buffer.MemoryCopy`. A buffer filled completely is doubled; a buffer grown above the maximum is shrunk back when it can be ([NetworkHandler.cs#L326-L342](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/NetworkHandler.cs#L326-L342), [L517-L556](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/NetworkHandler.cs#L517-L556)). So a request is always contiguous in memory.
- **Send buffers.** Each is a `GarnetSaeaBuffer`: a `SocketAsyncEventArgs` bound to one pooled pinned buffer ([GarnetSaeaBuffer.cs#L29-L36](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/GarnetSaeaBuffer.cs#L29-L36)). They are recycled through a per-connection stack of capacity 2 × the throttle limit, guarded by a `SpinLock` ([GarnetTcpNetworkSender.cs#L32](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/GarnetTcpNetworkSender.cs#L32), [L68-L86](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/GarnetTcpNetworkSender.cs#L68-L86); [LightConcurrentStack.cs#L15-L30](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/LightConcurrentStack.cs#L15-L30)).

### 8.3 Parsing in place

- `TryProcessRequest` passes the session a raw pointer to the unconsumed bytes and the count, and advances by however many bytes the session consumed ([NetworkHandler.cs#L504-L515](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/NetworkHandler.cs#L504-L515)).
- `RespServerSession.ProcessMessages` parses commands one after another from that pointer. On an incomplete command it rewinds to the command's start and stops, leaving the bytes for the next receive ([RespServerSession.cs#L613-L638](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Resp/RespServerSession.cs#L613-L638)).
- Arguments are pointer slices into the receive buffer ([arenas-zero-alloc.md](arenas-zero-alloc.md) Pattern C), valid only during this pass.
- The paper describes the parser as predictive: it checks the most common commands first and exploits RESP's regular syntax to cut branches ([Garnet paper §3.2](https://www.vldb.org/pvldb/vol19/p224-chandramouli.pdf)).

### 8.4 Batching all responses into one send

- **One buffer per receive pass.** At the start of `TryConsumeMessages` the session takes the connection's send lock and one send buffer, keeping raw `dcurr` and `dend` write pointers into it ([RespServerSession.cs#L469-L483](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Resp/RespServerSession.cs#L469-L483); [GarnetTcpNetworkSender.cs#L120-L134](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/GarnetTcpNetworkSender.cs#L120-L134)).
- **Writing.** Every response writer is a `TryWrite…(…, ref dcurr, dend)` that fails when out of room. The caller loops: `SendAndReset` sends what is there, takes a fresh buffer and retries. It throws only if a single response cannot fit an empty buffer ([L1318-L1334](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Resp/RespServerSession.cs#L1318-L1334)).
- **Flush at the end.** After the last complete command in the received bytes, one `Send` covers all responses written for that batch ([L712-L722](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Resp/RespServerSession.cs#L712-L722), [L1410-L1434](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Resp/RespServerSession.cs#L1410-L1434)). The lock is released and any unused buffer returned in `finally` ([L563-L569](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Resp/RespServerSession.cs#L563-L569)).
- **The send.** `SendResponse` hands the buffer to `socket.SendAsync`. The completion callback returns the buffer to the stack ([GarnetTcpNetworkSender.cs#L210-L229](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/GarnetTcpNetworkSender.cs#L210-L229), [L310-L338](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/GarnetTcpNetworkSender.cs#L310-L338)).
- **Backpressure.** At most `NetworkSendThrottleMax` sends (default 8) may be outstanding per connection; past that the sending thread blocks on a `SemaphoreSlim` until a send completes ([GarnetServerOptions.cs#L295-L301](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Servers/GarnetServerOptions.cs#L295-L301); [GarnetTcpNetworkSender.cs#L264-L282](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/GarnetTcpNetworkSender.cs#L264-L282), [L312-L320](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/GarnetTcpNetworkSender.cs#L312-L320)). The docs describe the same throttle ([network.md#L34-L38](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/website/docs/dev/network.md?plain=1#L34-L38)).

**Inference:** this is JSON-RPC.NET's "once per read group" flush (§0) with a different buffer model. Responses are written straight into a pinned, pooled buffer that becomes the socket send buffer, so no `PipeWriter` and no copy sit between the response bytes and `SendAsync`.

### 8.5 Threading model: processing on the completion thread

- **Paper.** A session's network buffers are processed by the thread that receives them, for instance the OS thread-pool thread that handles the network interrupt. A batch of commands from one packet runs "without any thread-switching (except for disk IO)" ([Garnet paper §3.1](https://www.vldb.org/pvldb/vol19/p224-chandramouli.pdf), [§3.3](https://www.vldb.org/pvldb/vol19/p224-chandramouli.pdf)).
- **Code.** The receive callback loops `do { OnNetworkReceive…; } while (!ReceiveAsync(e))` and runs the parsing and storage work synchronously inside it ([TcpNetworkHandlerBase.cs#L212-L232](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/TcpNetworkHandlerBase.cs#L212-L232)). The handler's comment reads "Process non-TLS code on the synchronous thread" ([NetworkHandler.cs#L272-L284](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/NetworkHandler.cs#L272-L284)). Only the first receive, if it completes synchronously, is pushed to `Task.Run`, so it does not hold up the accept loop ([TcpNetworkHandlerBase.cs#L127-L149](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/TcpNetworkHandlerBase.cs#L127-L149)).
- **Tuning.** Thread-pool worker and I/O-completion thread minimums and maximums are exposed as server options and applied at startup ([GarnetServer.cs#L205-L225](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/host/GarnetServer.cs#L205-L225); [GarnetServerOptions.cs#L255-L258](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/server/Servers/GarnetServerOptions.cs#L255-L258)).
- **TLS.**
  - TLS runs through an `SslStream` over an internal stream adapter with two semaphores ([NetworkHandler.cs#L115-L139](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/NetworkHandler.cs#L115-L139), [L290-L324](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/NetworkHandler.cs#L290-L324)).
  - The synchronous start blocks on the TLS handshake ([L147-L157](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/NetworkHandler.cs#L147-L157)), and the read path blocks on a decrypt that has already completed ([L362-L397](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/NetworkHandler.cs#L362-L397)).
  - TLS gets a separate decrypted-bytes receive buffer and send buffer ([L121-L135](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/libs/common/Networking/NetworkHandler.cs#L121-L135)).
- **Shadowfax**, the earlier FASTER-based networked store, made the same choice with pinned polling threads: each thread polls its connections, executes requests against the shared FASTER instance and replies on the same session, and "neither requests nor results are ever passed across server threads" ([Shadowfax §3.1](https://www.vldb.org/pvldb/vol14/p1427-kulkarni.pdf)).

### 8.6 Published network-layer figures

- **Allocation.** The network-level benchmarks drive an embedded network handler with no real socket, one command per call ([NetworkBase.cs#L31-L36](https://github.com/microsoft/garnet/blob/e5ae3e8e943297b6f343c18dd5aacf0153cc942e/benchmark/BDN.benchmark/Network/NetworkBase.cs#L31-L36)). ## 10. Applicability to GRPC.NET

Labels: **Verified** points restate sections 0 to 9. **Inference** points are the author's reading.

### 10.1 Epochs as an alternative to reference counts or leases

- **Verified.**
  - Epoch protection is held by an OS thread, entered and left around short synchronous regions; `BasicContext` brackets every single operation (§1.2, §4.2).
  - Re-entrancy is forbidden, and task code must avoid inline continuations (§1.4).
  - Reclamation waits for the slowest protected thread (§1.1).
- **Inference: where epochs fit in GRPC.NET.**
  - **Swapping read-mostly shared state.** Examples: the method table when services are registered or reloaded, the per-host settings snapshot, or a pool trimming its free lists. Readers would refresh an epoch instead of taking a reader lock or bumping a shared counter, which avoids the cache-line ping-pong EPVS describes.
  - **Per-thread scratch reclaimed lazily.** Freeing a thread's scratch when the pool shrinks can be a trigger action rather than a lock.
  - **Cost.** Both are rare-write, read-everywhere cases, the case where epochs cost almost nothing.
- **Inference: where epochs do not fit.**
  - **Buffers that outlive an `await`.** That includes request bytes held by a streaming method, a leased `bytes` field (R3 item 5), or a response staged while a method awaits.
  - **Why.** A protected region cannot cross an `await`, because the slot is keyed to the thread. Holding the epoch for the life of a stream would stall reclamation for every other stream, and a slow client would become everyone's memory leak.
  - **What to keep.** JSON-RPC.NET's transferable leases and Orleans-style reference-counted pages (arenas note, Patterns E and F) remain the right tools for anything that crosses an await. That agrees with R3 and R4.
- **Inference: HTTP/2 buffers shared across streams.** The case where several streams' frames share one connection-level receive block is exactly where Kestrel copies into per-stream pipes ([RESEARCH-MEMORY.md](../../RESEARCH-MEMORY.md) finding 6). An epoch could guard such a block only if every consumer finishes synchronously inside the read pass, which is true for unary calls on the synchronous fast path and false otherwise. A built-in host could use "sync consumers borrow, async consumers copy", the same split R3 makes for messages.

### 10.2 Tail reservation and group commit as a model for batched frame writes

- **Verified.**
  - TsavoriteLog lets many threads reserve space with one fetch-and-add and copy their bytes in parallel (§6.1).
  - It finds the fully written prefix through per-thread in-flight marks (§6.2), and commits that prefix in groups under a policy of count, time or bytes, with one TCS per commit shared by every waiter (§6.3).
  - The FasterLog and CPR results show the single tail becoming the bottleneck as writer threads grow (§6.5).
  - Garnet's network layer does not use the log for sends. It batches by having one thread own the send buffer for a whole receive pass (§8.4).
- **Inference: a mapping to a built-in HTTP/2 host.**
  - **Reserve.** A connection's outgoing bytes could be a ring of pinned pages with a `PageOffset`-style tail. A stream completing on any thread would reserve `9 + payload` bytes (frame header plus data) with one `Interlocked.Add` and write its DATA frame straight into place.
  - **Publish.** It would publish an in-flight mark, as TsavoriteLog does, so the connection's single sender could send `[sent, safeTail)` in one `SendAsync`.
  - **Effect.** This removes Kestrel's per-stream pipe copy and channel hand-off ([RESEARCH-MEMORY.md](../../RESEARCH-MEMORY.md) finding 6) and gives "as few socket writes as possible" across streams.
- **Inference: what HTTP/2 adds that a log does not have.**
  1. **HPACK ordering.** Header blocks must be encoded in wire order whenever the dynamic table is used. A writer either serializes header encoding under a lock, or encodes response headers without dynamic-table insertions so that blocks are order-independent; RFC 7541 permits the latter. It would cost some compression on repeated response metadata.
  2. **Per-stream order.** HEADERS before DATA before trailers. A unary response written as one reservation of all three frames keeps that for free.
  3. **Flow control.** Send windows must be checked before reserving, and a window-blocked stream must not hold a reservation; otherwise it stalls the safe tail for everyone, the analogue of a slow epoch holder.
  4. **Contention.** One connection is usually driven by one receive thread at a time (§8.5), so the fetch-and-add is mostly uncontended. It contends only when async continuations from many threads complete on the same connection, which is the case worth measuring.
- **Inference: commit policy maps to flush policy.** Garnet and JSON-RPC.NET flush at the end of a receive pass. A TsavoriteLog-style `RateLimit(ms, bytes)` policy is the analogue for responses that complete outside a receive pass (async methods, server streams): flush when the input runs dry, or when N bytes or T µs have accumulated, whichever comes first. A sync waiter should wait on one shared completion per flush, not per message.
- **Inference: Kestrel host.** A Kestrel-hosted GRPC.NET cannot use any of this below the `PipeWriter`. It can still follow Garnet's rule above it: write all of a pass's responses before one `FlushAsync`, as JSON-RPC.NET does.

### 10.3 The struct-generic Functions pattern for the codec seam and dispatch

- **Verified.**
  - Tsavorite passes callbacks as struct type parameters with `ref` arguments so that the JIT specializes and inlines them (§4.1).
  - It uses a struct wrapper over a class to get the same effect for class implementations (§4.1).
  - It keeps the in-memory path allocation-free and gates that in CI (§4.3, §8.6).
- **Inference.** This is direct support for R5's "struct-generic implementations avoid interface dispatch".
  - **Codec seam.** For example `Process<TCodec>(…) where TCodec : struct, IGrpcCodec<TReq, TResp>`, with `ref` or `in` request and response parameters.
  - **Generated method stubs.** Each method could be a `readonly struct` invoker, and the per-path table could store a closed generic delegate created once at registration, so the hot path makes one indirect call into fully specialized code.
  - **Classes.** A user's codec or service class can still be wrapped in a generated struct, as Tsavorite does for its allocator.
- **Inference: the cost.** Every distinct struct instantiation is a separate JIT body. With hundreds of methods this grows code size and start-up time, and Native AOT must see every instantiation at compile time. Generated code (R5's source generator) makes the instantiations explicit, which suits AOT.
- **Inference: the CI gate.** Garnet's "allocated bytes must not exceed the expected value by more than 10%" gate is a cheap, concrete way to hold GRPC.NET's "no allocation per call" claim. It fits the benchmark controls in [RESEARCH-MEMORY.md](../../RESEARCH-MEMORY.md).

### 10.4 Garnet's host as evidence on the optional built-in hosting mode

- **Evidence for.**
  - **Verified.** A production .NET server reaches tens of millions of operations per second with a raw-socket host that processes on the receiving thread, writes responses into pooled pinned buffers and sends once per pass (§8).
  - **Verified.** Garnet's own design study found that adding thread hand-offs between network and storage cut throughput from 47 to 4.4–9 Mops/s (§8.6).
  - **Verified.** Shadowfax reached the same conclusion with polling threads (§8.5).
  - **Inference.** Kestrel dispatches each HTTP/2 stream to the thread pool and passes each response through a channel to the connection's writer ([RESEARCH-MEMORY.md](../../RESEARCH-MEMORY.md) finding 6). Those are the kinds of hand-off Garnet measured as expensive. A built-in host that runs unary calls inline on the receive thread could be worth a large factor.
- **Evidence against, or for caution.**
  - **Verified.** Garnet speaks RESP: pipelined, strictly FIFO and unmultiplexed (§8.3, paper §3.1). HTTP/2 adds HPACK state, per-stream and per-connection flow control, SETTINGS, PING, RST_STREAM, GOAWAY, priorities, h2c and ALPN negotiation.
  - **Verified.** Garnet's TLS path blocks threads on synchronous waits (§8.5), its throttle blocks the network thread (§8.4), and its accept backoff sleeps on the accepting thread (§8.1).
  - **Inference.** These are acceptable for a cache whose handlers never await, but not for a framework that runs user `async` methods.
  - **Verified.** No source here compares Garnet's host with Kestrel, and Garnet's headline figures all rely on deep client pipelining (§9).
  - **Inference.** The evidence supports the README's position as written: a built-in mode only if measured. The measurement should isolate the hand-offs Garnet measured, comparing the core behind Kestrel against the core behind a minimal socket host on the same unary, pipelined workload, before any HTTP/2 framing work is costed.

### 10.5 What not to borrow

**Inference**, each grounded in the cited code:

- **Raw pointers over pinned memory as the general programming model** (`byte*` request pointers, `dcurr` and `dend`, `PinnedSpanByte`; §5, §8.3–8.4). This conflicts with FlatSharp's "safe code by default" lesson ([RESEARCH-MEMORY.md](../../RESEARCH-MEMORY.md) finding 4). If a built-in host ever uses pinned send buffers, the `unsafe` code should stay inside the host, and the core should see only `Span<byte>` and `IBufferWriter<byte>`.
- **Sync-over-async on I/O threads**: blocking waits for TLS, for the log commit before send, and for the send throttle (§6.3, §8.4–8.5). GRPC.NET runs user code that awaits, so it needs asynchronous backpressure. This is CALL-INTERFACE.md open question 5.
- **Epochs across awaits**, or as a general substitute for ownership tracking (§10.1).
- **Fixed global limits without clear failure modes**: 1,024 epoch instances per process, a 16-slot drain list that spins when full, an epoch table that blocks when full (§1.2). These are fine inside one storage engine and surprising inside a library that applications embed several times.
- **Clearing every returned 128 KiB network buffer** (§8.2). That is a memory-bandwidth cost per return. JSON-RPC.NET's pools and Kestrel's do not clear on return, and the arenas note's mitigation (poisoning in a debug pool) is cheaper for catching use after return.
- **The engineering cost of hand-written latch-free state machines** (EPVS's "months", §1.4). GRPC.NET's core has no shared mutable index; most of its state is per call or per connection. Where shared state exists, a plain lock or an immutable snapshot should be the default until a profile shows contention.

### 10.6 Agreement and conflict with R1 to R6

| Recommendation | Relation | Detail |
| --- | --- | --- |
| R1 (sequence in, decode from a span, copy a split message once into scratch) | **Agrees, with an alternative for a built-in host** | Garnet avoids sequences entirely: one contiguous per-connection receive buffer that is shifted and doubled, so every request is a span (§8.2). That costs 128 KiB or more per connection and a `MemoryCopy` per pass with leftovers. Under Kestrel, R1 stands. A built-in host could choose Garnet's model and pass `IsSingleSegment` sequences always, making R1's copy path cold (**Inference**). |
| R2 (measure, then write the prefix and message) | **Agrees** | TsavoriteLog must know an entry's exact length before the fetch-and-add reserves it (§6.1). | R3 (owned by default, compiler-checked borrowing opt-in) | **Agrees** | Garnet's borrowed pointer slices are valid only during the synchronous pass (§8.3), the same constraint R3 puts on `ref struct` views. Epochs do not extend borrowing across awaits (§10.1). |
| R4 (pool bytes, not message objects; no core-owned pinned or native memory in the first release) | **Agrees for the core; conflicts for a built-in host** | Garnet pools only infrastructure objects: send-buffer wrappers, heap containers, `Overlapped` structures (§4.3, §7, §8.2), never values. | R5 (codec seam, struct generics, Google.Protobuf first) | **Agrees, strongly** | Tsavorite's struct-generic callbacks and struct-over-class wrapper are a production precedent for the seam (§4.1, §10.3). |
| R6 (strings: copy by default, UTF-8 views, a cache for repeated values) | **Agrees** | Tsavorite and Garnet never materialize keys as `string`; they compare and hash bytes (§5). That supports UTF-8 views and byte-keyed caches. |

### 10.7 What to measure before adopting any of this

**Inference:**

1. **Hand-off cost under Kestrel.** Unary calls through the GRPC.NET core behind Kestrel, against the same core behind a minimal raw-socket host that processes inline and flushes once per pass. Use 1 and 256 calls in flight per connection, with allocated bytes per call. This is Garnet's §8.5 study transposed.
2. **Flush policy.** Responses per `SendAsync` and P99 latency for flush-at-end-of-pass against a bytes-or-microseconds threshold, with async methods mixed in.
3. **Tail contention.** Reserving DATA frames with a fetch-and-add per connection, when completions arrive from 1, 4 and 16 threads on one connection.
4. **Epoch versus lock for the method table.** Only if registration at run time is supported; otherwise an immutable table needs neither.
