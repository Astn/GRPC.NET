# FlatSharp: prior art for GRPC.NET

FlatSharp is a FlatBuffers serializer for C# by James Courtney, licensed Apache 2.0. These notes record what it does about allocation, buffer ownership, code generation and gRPC, and what GRPC.NET can learn from it.

## 1. Deserialization modes

### How the modes are built

- **[V] Parsing returns a generated subclass.**
  - Parsing returns a generated subclass of the schema type, whose virtual properties read from the buffer. The mode decides how those overrides work. Sources: `B/README.md#L98-L101` and `W/Deserialization-Modes` ("FlatSharp: How it works").
  - The tables and structs FlatSharp generates are therefore always classes. Only structs marked `fs_valueStruct` are C# value types; unions are value types unless pooling was enabled. Source: [#339](https://github.com/jamescourtney/FlatSharp/issues/339), opening post.
- **[V] The four modes, and the default.**
  - The modes are `Lazy`, `Progressive`, `Greedy` and `GreedyMutable`. `Default` is `GreedyMutable`. Source: `B/src/FlatSharp.Runtime/FlatBufferSerializationOption.cs#L22-L48`.
  - No other mode exists in 7.9.0.
  - The mode is chosen per call (`Parse(buffer, option)`), or per serializer instance with `WithSettings(s => s.UseLazyDeserialization())`. Sources: `B/src/FlatSharp.Runtime/GeneratedSerializerWrapper.cs#L102-L143` and `B/src/FlatSharp.Runtime/SerializerSettings.cs#L39-L63`.
- **[V] One entry point per mode.** The generated serializer exposes `ParseLazy`, `ParseProgressive`, `ParseGreedy` and `ParseGreedyMutable`. The wrapper switches on the option. Source: `B/src/FlatSharp.Runtime/IGeneratedSerializer.cs#L61-L82` and `GeneratedSerializerWrapper.cs#L119-L140`.
- **[V] Trimming generated code.** All four modes are generated by default. The `FlatSharpDeserializers` MSBuild property limits generation to the modes you list, to cut code size. Source: `W/Compiler` ("Specifying Deserializers").

### What each mode allocates and keeps

| Mode | What it allocates, and when | Keeps a reference to the input buffer | Mutable | Documented trade-off |
| --- | --- | --- | --- | --- |
| `Lazy` | One object for the root. Each property read re-reads the buffer. Every access to a table, reference struct or string allocates a new instance; the sample asserts that two reads of `Name` return different objects. | Yes: the buffer, the offset and the decoded vtable | No, except write-through fields | Fastest for sparse, read-once access. Gets slow on repeated access. |
| `Progressive` | Allocates on first access, then caches the value behind a has-value bit mask. Vectors use a sparse cache. | Yes | No, except write-through fields | A safe default when the access pattern is unknown. Never the slowest, and seldom the fastest. |
| `Greedy` | The whole object graph during `Parse`. Vectors become `ImmutableList<T>`. | No | No | Behaves like a conventional serializer. The buffer can be recycled at once. Large graphs cause GC spikes. |
| `GreedyMutable` (default) | Same as `Greedy`. Vectors become `List<T>`. | No | Yes | Same as `Greedy`. Chosen as the default because it behaves like other serializers. |

Sources for the table:

- `W/Deserialization-Modes`, sections "GreedyMutable", "Lazy", "Progressive" and "Performance Implications".
- `W/Vectors`, the "Lists" table.
- `B/samples/Example01-DeserializationModes/DeserializationModes.cs#L91-L117` (Lazy) and `#L130-L158` (Progressive).
- `B/src/FlatSharp/Serialization/DeserializeClassDefinition.cs#L66-L89`: Greedy decodes the vtable in the constructor and does not keep it; the other modes store it.

### Measured allocations

**[V] Allocation per parse-and-traverse.** These figures come from FlatSharp's own 7.0.0 results for a 30-item message (.NET 7, Ryzen 9 5950X). Source: `B/benchmarks/7.0.0/Benchmark.FBBench.FBDeserializeBench-report-github.md`.

| Mode | Allocated, reference structs | Allocated, value structs |
| --- | --- | --- |
| Lazy | 7.95 KB | 6.08 KB |
| Progressive | 10.3 KB | 8.43 KB |
| Greedy and GreedyMutable | 8.5 KB | 7.56 KB |

**[I] Lazy is not allocation-free.** Lazy pays for a fresh object and a fresh string on every access. The author has said strings cannot be read without allocating ([#339](https://github.com/jamescourtney/FlatSharp/issues/339#issuecomment-1310096506)). Allocation-free reads would need value-type access with no string materialization.

### Limits

**[V] Built-in limits.**

- `Parse` rejects buffers of 1 GB or more, and buffers of 8 bytes or less. Source: `GeneratedSerializerWrapper.cs#L104-L112`.
- An object depth limit (default 1000) guards against stack overflow from malicious input. Source: `GeneratedSerializerWrapper.cs#L45` and `SerializerSettings.cs#L115-L120`.

## 2. Input and output buffer abstractions

### Reading: `IInputBuffer`

**[V] The interface.** `IInputBuffer` exposes scalar reads at an offset and `ReadString(offset, length, encoding)`. It also exposes `GetReadOnlySpan`, `GetSpan`, `GetReadOnlyMemory` and `GetMemory`, and the flags `IsReadOnly` and `IsPinned`. Its doc comment says implementations are fastest as structs. Source: `B/src/FlatSharp.Runtime/IO/IInputBuffer.cs#L21-L115`.

**[V] Structs specialized through generics.** Every parse entry point is generic over `TInputBuffer : IInputBuffer` (`ISerializer.cs`, `Parse<TInputBuffer>`). Generated reader classes are generic over it too (`W/Deserialization-Modes`, `LocationReader<TInputBuffer>`). The JIT therefore specializes the code for each struct buffer and does not dispatch through the interface.

**[V] The shipped implementations are all structs.**

| Type | Wraps | Notes |
| --- | --- | --- |
| `ArrayInputBuffer` | `byte[]` | Holds the array directly. Source: `B/src/FlatSharp.Runtime/IO/ArrayInputBuffer.cs#L24-L30`. |
| `ArraySegmentInputBuffer` | `ArraySegment<byte>` | Boxes the segment into a small private class. Source: `IO/ArraySegmentInputBuffer.cs#L137-L139`. |
| `MemoryInputBuffer` | `Memory<byte>` (optionally pinned) | Wraps the `Memory<byte>` in a small private class, on the stated grounds that this is cheaper than copying a large struct around. Source: `IO/MemoryInputBuffer.cs#L141-L148`. |
| `ReadOnlyMemoryInputBuffer` | `ReadOnlyMemory<byte>` | `GetSpan` and `GetMemory` throw. Write-through and `Memory<byte>` vector fields therefore fail at run time, which guarantees the input is never modified. Source: `IO/ReadOnlyMemoryInputBuffer.cs#L20-L27` and `#L135-L144`. |

`ISerializerExtensions` has `Parse` overloads for `byte[]`, `ArraySegment<byte>`, `Memory<byte>` and `ReadOnlyMemory<byte>`. Source: `B/src/FlatSharp.Runtime/ISerializerExtensions.cs#L40-L117`.

**[V] Buffer types that do not exist.**

- There is no buffer over unmanaged pointers in the runtime (`src/FlatSharp.Runtime/IO/` has only the four types above).
- There is no buffer over `ReadOnlySequence<byte>`. The author built a prototype in [#380](https://github.com/jamescourtney/FlatSharp/issues/380) and rejected it, for two reasons:
  - FlatBuffers reads jump randomly, so each scalar read must copy across segment boundaries.
  - `IInputBuffer` must be able to return the whole buffer as one span.
- His advice there is to copy the sequence into a pooled contiguous array and parse that.

**[I] Allocation cost of each wrapper.** `Memory<byte>` and `ArraySegment<byte>` cost one small allocation per buffer instance; `byte[]` costs none.

### How reads avoid copies, and how they are bounds-checked

**[V] Reads.**

- Every scalar read slices a span (`memory.AsSpan().Slice(offset)`) and decodes with `BinaryPrimitives.Read*LittleEndian`. Each read is therefore bounds-checked by the span. Sources: `IO/ArrayInputBuffer.cs#L42-L104` and `B/src/FlatSharp.Runtime/IO/ScalarSpanReader.cs`.
- Floats are reinterpreted through an explicit-layout union struct, not through unsafe code. Source: `ScalarSpanReader.cs#L115-L122`.
- Strings are decoded straight from the span with `Encoding.GetString(span)`. On netstandard2.0 they go through an `ArrayPool` rental. Source: `ScalarSpanReader.cs#L101-L112`.
- Alignment checks run only in DEBUG builds. Source: `B/src/FlatSharp.Runtime/IO/InputBufferExtensions.cs#L134-L142`.

**[V] Validation.**

- Offsets are validated: a uoffset smaller than 4 throws. Source: `InputBufferExtensions.cs#L62-L71`.
- A vtable shorter than 4 bytes throws. Source: `InputBufferExtensions.cs#L77-L94`.
- Arithmetic is `checked` in places, for example `ReadString` (`#L40-L48`) and `SerializationHelpers.GetMaxSize(string)`.

**[V] Narrow use of `MemoryMarshal`.**

- Small vtables are read in one shot with `MemoryMarshal.Read<VTable4>`. Source: `B/src/FlatSharp.Runtime/VTables/VTable4.cs#L123-L131`.
- Value-struct vectors are reinterpreted with `MemoryMarshal.Cast`. Source: `InputBufferExtensions.cs#L117-L129`.
- The README's security section promises no unsafe code and bounds-checked operations, and says `MemoryMarshal` is used narrowly on hot paths. Source: `B/README.md#L103-L111`.
- Truly unsafe code is opt-in, per schema element: `fs_unsafeStructVector`, `fs_unsafeUnion` and `fs_unsafeExternal`. Source: `W/FBS-Annotations`. The runtime project does not set `AllowUnsafeBlocks`.

**[V] Zero-copy byte vectors.** A `[ubyte]` vector maps to `Memory<byte>` by default. In Lazy and Progressive modes it is a slice of the input buffer with no copy (`ReadByteMemoryBlock`, `InputBufferExtensions.cs#L98-L113`). Greedy modes copy it. Source: `W/Vectors` ("Memory").

### Writing: `ISpanWriter`

**[V] The interface.** `ISpanWriter` writes scalars into a caller-provided `Span<byte>` at absolute offsets. It also provides `GetStringBytes` and `FlushSharedStrings`. Source: `B/src/FlatSharp.Runtime/IO/ISpanWriter.cs`.

**[V] The default implementation.** `SpanWriter` is a struct that uses `BinaryPrimitives.Write*LittleEndian` on sliced spans, so writes are bounds-checked too. It encodes strings directly into the destination with `encoding.GetBytes(value, destination)`. Source: `B/src/FlatSharp.Runtime/IO/SpanWriter.cs#L62-L110`.

**[V] Serialization writes one contiguous span, front to back.**

- `GetMaxSize(item)` returns an upper bound.
  - Strings are counted with `Encoding.GetMaxByteCount`, which for UTF-8 is about three bytes per character.
  - Sources: `GeneratedSerializerWrapper.cs#L63-L84` and `B/src/FlatSharp.Runtime/SerializationHelpers.cs#L43-L52`.
- `Write` returns the bytes actually written.
- A buffer that is too small throws `BufferTooSmallException`, which carries the size needed.
- Google's C# library, by contrast, builds back to front. Source: `W/Comparison-With-Google-FlatBuffers`.

**[V] `IBufferWriter<byte>` support is a thin wrapper.** It calls `GetMaxSize`, then `bufferWriter.GetSpan(maxSize)`, writes, and calls `Advance(bytesWritten)`. Source: `B/src/FlatSharp.Runtime/ISerializerExtensions.cs#L198-L207`.

**[V] Per-call state lives in a reused thread-local context.**

- `SerializationContext` is `ThreadLocal` and reset per call. It holds the write offset, post-serialize actions and the list of vtable offsets. Source: `B/src/FlatSharp.Runtime/SerializationContext.cs#L32-L73`.
- Vtables are deduplicated by linear search with move-to-front. Source: `SerializationContext.cs#L152-L200`.
- Serializing allocates nothing in FlatSharp's own run: `FlatSharp_Serialize` shows `Allocated = -`. Source: `B/benchmarks/7.0.0/Benchmark.FBBench.FBSerializeBench-report-github.md`.

**[V] Memory-copy serialization (experimental).** Serializing an object that was itself deserialized can be a plain memory copy of its retained input buffer. This works for Lazy and Progressive objects. Sources: `SerializerSettings.cs#L104-L113`, `GeneratedSerializerWrapper.cs#L160-L174` and `B/src/FlatSharp.Runtime/IFlatBufferDeserializedObject.cs`.

## 3. How the generated code is produced

**[V] A build-time compiler, not a source generator.**

- `FlatSharp.Compiler` is an executable for net6.0 to net10.0 (`B/src/FlatSharp.Compiler/FlatSharp.Compiler.csproj#L4-L7`). It bundles the official `flatc` for Windows, Linux and macOS (`#L27-L50`).
- An MSBuild target runs `dotnet FlatSharp.Compiler.dll --input <fbs>` through `Exec` before `ResolveAssemblyReferences`. It adds the output `.cs` files to `Compile`. Source: `B/src/FlatSharp.Compiler/FlatSharp.Compiler.targets#L92-L178`.
- The pipeline is described in `W/Architecture` ("FlatSharp Compiler"):
  1. `flatc` parses the `.fbs` file.
  2. The compiler emits C# classes.
  3. Roslyn compiles them at build time (`B/src/FlatSharp.Compiler/FlatSharpCompiler.cs#L361`).
  4. The attribute-based type model generates serializer C#, which is spliced back in.
- A Roslyn source generator was considered for v7 and struck from the plan ([#276](https://github.com/jamescourtney/FlatSharp/issues/276)).
- The emitted code targets C# 8 and is checked in CI. Source: `W/Testing`.

**[V] Schema source.**

- Only `.fbs` schemas are supported.
- The older runtime mode, which built serializers from C# attributes through reflection and in-memory Roslyn compilation, was dropped in 7.0.
- The reasons given were AOT and Unity support, no Roslyn dependency, no runtime code-generation cost, and errors caught at build time.
- `FlatSharp.Runtime` now makes no reflection calls.

Source: [7.0.0 release notes](https://github.com/jamescourtney/FlatSharp/releases/tag/7.0.0) ("Runtime-Only Mode Deprecation").

**[V] AOT and trimming.**

- `FlatSharp.Runtime` targets netstandard2.0 through net10.0 and depends only on `System.Memory`. It sets `IsAotCompatible` for net9.0 and net10.0. Source: `B/src/FlatSharp.Runtime/FlatSharp.Runtime.csproj#L4-L31`.
- The full test suite runs under NativeAOT in CI on three operating systems. Source: `W/Testing`.
- NativeAOT benchmark numbers are published alongside the JIT numbers. Source: `B/README.md#L130-L149`.

**[V] Duplicated code per root type.**

- Each root type gets its own copy of the parse and serialize code for everything it reaches.
- The author names gRPC as the worst case, since every request and response type is a root.
- He notes the cost in instruction cache and branch prediction. Source: [#276](https://github.com/jamescourtney/FlatSharp/issues/276), "Rework FBS Codegen".

**[I] Why this matters for GRPC.NET.**

- Build-time generation removes startup cost and any dependency on `System.Reflection.Emit` or Roslyn at run time. That is the precondition for Native AOT and trimming.
- A build-time `Exec` of a separate tool has drawbacks:
  - It needs a .NET runtime on the build machine.
  - It runs outside the IDE's incremental generator model.
  - It ties a compiler version to a runtime version. The author resists shipping it as a `dotnet` tool for that reason ([#448](https://github.com/jamescourtney/FlatSharp/issues/448)).
- A Roslyn incremental source generator would avoid the external-process step. For a C#-first contract, an attribute-driven generator fits the JSON-RPC.NET programming model better than `.fbs` or `.proto` plus `Exec`.

## 4. Pooling, value structs, write-through, shared strings and vectors as views

### Object pooling: tried and removed

**[V] History.**

- Pooling was experimental in 7.0 and removed in 7.8.0. Sources: `W/Object-Pooling` and the [7.8.0 release notes](https://github.com/jamescourtney/FlatSharp/releases/tag/7.8.0).
- **Cost.** The author's prototypes ran at roughly half the speed of the unpooled path on .NET 7 ([#339 comment](https://github.com/jamescourtney/FlatSharp/issues/339#issuecomment-1310096506)). He argued that pools pay off only for expensive objects, and FlatSharp's objects are cheap.
- **Hazards.** The wiki lists double-return, use-after-return across threads, and generated return methods that are not thread-safe.
- **Rules that depended on the mode.** In Lazy mode every object had to be returned individually. In the other modes, returning the root returned the tree.

### Value structs (`fs_valueStruct`)

**[V]**

- Value structs generate C# structs with explicit layout and no GC allocation.
- On little-endian machines they can be read and written with a single `MemoryMarshal.Cast`; the `fs_memoryMarshal` attribute tunes this.
- In every mode, a value struct is parsed greedily when it is accessed.
- Sources: `W/FBS-Annotations` (`fs_valueStruct`, `fs_memoryMarshal`) and `B/samples/Example13-ValueStructs/ValueStructs.cs#L19-L34`.
- In the 7.0.0 run they cut allocation by about 1.9 KB per parse in Lazy mode (section 1).

### Write-through (`fs_writeThrough`)

**[V]**

- Setters on Lazy and Progressive objects write straight into the input buffer, so small edits need no parse and re-serialize.
- It applies to fields of reference structs, required value-struct table fields, and value-struct vectors. A vector's length cannot change.
- It requires a writable buffer: `ReadOnlyMemoryInputBuffer` throws.
- Sources: `W/FBS-Annotations` (`fs_writeThrough`) and `B/samples/Example12-WriteThrough/WriteThrough.cs#L26-L42`.

### Shared strings (`fs_sharedString`)

**[V]**

- Shared strings deduplicate strings at write time.
- Each serializer keeps one thread-local writer: a direct-mapped hash table with 1019 slots that flushes on eviction.
- The feature saves space, not time, and the wiki says LZ4 usually compresses better.
- Sources: `W/Shared-Strings`, `B/src/FlatSharp.Runtime/IO/SharedStringWriter.cs#L19-L45` and `GeneratedSerializerWrapper.cs#L44`.

### Vectors as views

**[V]**

- `IList<T>` and `IReadOnlyList<T>` vectors are lazy views over the buffer in Lazy and Progressive modes.
- `Memory<byte>` and `ReadOnlyMemory<byte>` vectors point into the input buffer with no copy.
- `IIndexedVector` gives dictionary-style lookup over sorted vectors.
- Sources: `W/Vectors` and `W/Indexed-Vectors`.

### Lifetime and ownership rules a caller must follow

**[V] Reusing the buffer is undefined behaviour in Lazy and Progressive modes.**

- Lazy and Progressive objects keep a reference to the input buffer.
- Overwriting or recycling that buffer while the object is still in use is undefined behaviour.
- The samples zero the buffer and show that later reads throw an arbitrary exception. They might equally return wrong data.
- Progressive is unsafe too: anything not yet cached is still read from the buffer.
- Sources: `B/samples/Example01-DeserializationModes/DeserializationModes.cs#L113-L117` and `#L151-L158`, and `W/Deserialization-Modes`, Question 2.

**[V] Greedy objects are safe to keep.** Greedy and GreedyMutable objects keep no reference to the buffer, so the buffer may be reused as soon as `Parse` returns. Sources: `W/Deserialization-Modes` ("GreedyMutable") and `DeserializationModes.cs#L173-L184`.

**[V] `Memory<byte>` vector fields alias the input.** Writes through them change the original buffer, and they outlive the parse only as long as the buffer does. Source: `W/Vectors` ("When to avoid Memory<byte>").

**[V] Overlapping serialization is unsupported.** Serializing into the same buffer that a Lazy object is reading from was not designed for. The author expects the read and the write to race. Source: [#339 comment](https://github.com/jamescourtney/FlatSharp/issues/339#issuecomment-1310096506).

**[V] Write order.** `GetMaxSize` must be called, and the buffer sized, before `Write`.

**[I] The general rule.** Lazy deserialization is safe only if the deserialized object owns, or exclusively borrows, its buffer for its whole lifetime. Nothing in FlatSharp's API enforces this; it is documented, not typed.

## 5. gRPC integration

### What the compiler generates

**[V]** An `.fbs` `rpc_service` produces a `static partial class` named after the service. Source: `B/src/FlatSharp.Compiler/SchemaModel/RpcServiceSchemaModel.cs`. It contains:

- **Settable serializers.** A settable static `Serializer<T>.Value`, defaulting to each type's `.Serializer`. It lets the application swap in a serializer with different settings for each message type (`#L88-L103`, `#L118-L129`).
- **Marshallers.** One `Grpc.Core.Marshaller<T>` per message type, built with `Marshallers.Create` (`#L28-L38`, `#L137-L163`).
  - **Serialize:** `Serializer<T>.Value.Write(sc.GetBufferWriter(), item); sc.Complete();`.
  - **Deserialize:** `Serializer<T>.Value.Parse(new ArrayInputBuffer(dc.PayloadAsNewBuffer()))`.
- **Service binding.**
  - A `[BindServiceMethod]` attribute, `BindService(impl)` returning a `ServerServiceDefinition`, and a `BindService(ServiceBinderBase, impl)` overload (`#L201-L240`).
  - The `ServiceBinderBase` overload is the hook that grpc-dotnet's ASP.NET Core server uses to discover services. It was added in [PR #53](https://github.com/jamescourtney/FlatSharp/pull/53) for ASP.NET Core hosting.
- **Server base class.** Its abstract methods take `IAsyncStreamReader<T>`, `IServerStreamWriter<T>` and `ServerCallContext`, the same shapes as protobuf-generated services (`#L250-L265`).
- **Client.** A `ClientBase<T>` client. With `fs_rpcInterface`, it also gets an interface that wraps the streams in `System.Threading.Channels` `ChannelReader<T>` and `ChannelWriter<T>`, on the client only (`#L293-L320`; `W/FBS-Annotations`, `fs_rpcInterface`). A pump loop copies each message between the gRPC stream and the channel (`#L372-L411`).
- **Dependencies.** Only `Grpc.Core.Api` types are referenced, so the code runs on both the old `Grpc.Core` native server and grpc-dotnet. The sample uses `Grpc.Core`'s `Server`. Sources: `B/samples/Example04-gRPC/GrpcExample.cs#L43-L46` and `B/src/Directory.Packages.props#L11-L14`.

### What the marshaller contract allows

**[V]** From `Grpc.Core.Api` (`G/` = `https://github.com/grpc/grpc-dotnet/blob/7db6c142a2dd5e0fefb0681e67766e339a15dc47/`):

- **`PayloadAsNewBuffer`** returns a newly allocated array that the caller owns. The doc comment warns that it costs an extra copy, and that payloads over about 85 KB go to the large object heap. Source: `G/src/Grpc.Core.Api/DeserializationContext.cs#L33-L46`.
- **`PayloadAsReadOnlySequence`** avoids the copy. It is valid only while the deserializer runs. Source: `#L51-L61`.
- **`SetPayloadLength`** may be called before `GetBufferWriter()` to improve buffer sizing. FlatSharp does not call it. Source: `G/src/Grpc.Core.Api/SerializationContext.cs#L44-L64`.

### Inferences about the marshallers

- **[I] Copying in buys safe Lazy objects.** Calling `PayloadAsNewBuffer` gives every received message its own private array. That is what makes Lazy and Progressive objects safe to hand to user code under gRPC, which can keep them indefinitely. The price is one full copy and one array allocation per message, before any field is read.
  - The alternative is `PayloadAsReadOnlySequence`. It would need either a pooled copy, which lives only during the callback (unsafe for Lazy), or a sequence-backed buffer, which the author found slow ([#380](https://github.com/jamescourtney/FlatSharp/issues/380)).
- **[I] The worst-case size reservation is a real cost.**
  - The serialize side asks the gRPC buffer writer for a span of the worst-case size: `GetMaxSize`, with three bytes per string character. It does not compute the exact size.
  - With grpc-dotnet's pipe-backed writer, this can push a large message into an oversized or separate segment.
  - FlatBuffers cannot write the 5-byte length prefix before the payload is finished. The host must therefore buffer the payload, or reserve the prefix and patch it afterwards.
  - FlatSharp 8 planning briefly listed an exact-size API (`GetActualSize`) and then struck it ([#448](https://github.com/jamescourtney/FlatSharp/issues/448)).
- **[I] The generated client interface pays a channel operation per message.** The `fs_rpcInterface` pump turns each message into a channel write plus a channel read on top of gRPC's own stream. That is the per-message channel cost that CALL-INTERFACE.md rules out of the hot path.

### Configuration

**[V]** The sample sets three options for an echo service: memory-copy serialization, Lazy deserialization and shared strings. Echoed Lazy objects are then re-serialized as a straight copy of the received buffer. Source: `GrpcExample.cs#L30-L41`.

### Measured gRPC results

**[V] None found.**

- The repository has no gRPC benchmark. The `Grpc` packages appear in test, compile-test and microbenchmark projects, but no benchmark exercises a gRPC call; the main benchmark project references `Grpc.Tools` only to generate Google.Protobuf message classes.
- A search of the issues and pull requests for gRPC found feature work (#28, #53, #177, #183, #361) but no throughput or latency figures.
- There is no published evidence of FlatSharp-over-gRPC throughput against protobuf-over-gRPC.

## 6. FlatSharp's benchmarks

### Method

**[V]**

- **Harness.** BenchmarkDotNet with a `ShortRun` job: 7 process launches, 3 warmup and 5 measured iterations, launch-variance analysis, the memory diagnoser, and P25 and P95 columns. Source: `B/src/Benchmarks/Benchmark/Program.cs#L49-L68`.
- **Runtimes.** .NET 8 with PGO, plus a NativeAOT toolchain build (`#L40-L46`).
- **Workload.** A C# approximation of Google's FlatBuffers benchmark: a container holding a 30-item vector (`B/src/Benchmarks/Benchmark/FBBench/FBBenchCore.cs#L25-L26`).
  - Each item has a GUID string name, scalars and nested structs (`B/src/Benchmarks/Benchmark/Serializers/ProtobufHelper.cs#L26-L52`).
  - "ParseAndTraverse" reads every field 1 or 5 times (`TraversalCount`). "Partial" reads a subset.
- **Serialize measurement.** It writes into a buffer allocated beforehand (`B/src/Benchmarks/Benchmark/Serializers/FlatSharpHelper.cs#L49-L52`). `GetMaxSize` is measured separately: 138 ns against 1,213 ns for `Write` in the 7.0.0 data.
- **Package versions.** Google.Protobuf 3.25.3, protobuf-net 3.2.30, MessagePack 2.5.187 (`B/src/Directory.Packages.props#L10-L27`). Google.Protobuf parses with `Parser.ParseFrom(byte[])` and serializes with `CodedOutputStream` over a preallocated array.

### Caveats

- **[V] The author's own warning.** The README warns that a serializer-only microbenchmark does not reflect real programs, where the serializer competes for cache with everything else. It advises choosing a format by need (lazy access, size, hot path), not by benchmark rank (`B/README.md#L124-L125`).
- **[V] The headline table has no matching raw data.**

## 7. Other lessons for a high-throughput, low-allocation gRPC core

### Worth copying

- **Generic over struct buffers.**
  - **[V]** Every hot path is generic over `TInputBuffer : IInputBuffer` or `TSpanWriter : ISpanWriter`, and the implementations are structs.
  - **[I]** GRPC.NET's codec can do the same with a reader over `ReadOnlySpan<byte>` and a writer over `IBufferWriter<byte>`. The JIT then specializes the code with no interface dispatch.
- **Safe code by default, unsafe code opt-in.**
  - **[V]** Reads go through span slices, with checked arithmetic where offsets are combined, a depth limit and size limits. Unsafe code is opt-in for each schema element.
  - **[V]** The project backs this with fuzzing, mutation testing (95% of injected faults must be caught), oracle tests against Google's library, and NativeAOT CI (`W/Testing`).
  - **[V]** The author rejects speed-ups that weaken the overflow checks (`B/ProjectStatus.md`, "Performance Improvements").
- **Reused thread-local state.**
  - **[V]** The serialization context is reset per call, not allocated.
  - **[V]** Throw helpers marked `[DoesNotReturn]` (`B/src/FlatSharp.Runtime/FSThrow.cs`) keep the hot methods small.
- **Immutable serializer instances.**
  - **[V]** `WithSettings` returns a new serializer instance, so settings never change under a running call.
  - **[I]** GRPC.NET's method table can bind each method's codec once, when the service is registered, in the same way.
- **Re-send without re-encoding.**
  - **[V]** Memory-copy serialization of an object that was itself deserialized.
  - **[I]** An echo or proxy method could forward the request payload unchanged in the same way. This fits a byte-pipe core.
- **Build-time code generation and NativeAOT CI from the start.**

### Worth avoiding

- **Object pooling of message objects.** **[V]** FlatSharp tried it and removed it: slower, with use-after-return risk.
- **Random access over `ReadOnlySequence<byte>`.** **[V]** FlatSharp found it slow ([#380](https://github.com/jamescourtney/FlatSharp/issues/380)).
  - **[I]** Protocol Buffers decoding is sequential, so a sequence reader does work for protobuf.
  - **[I]** The cheaper path is still to parse a contiguous span: the gRPC length prefix gives the message size in advance, and most messages are small.
- **Worst-case size reservation.** **[I]** Reserving `GetMaxSize` space in a shared pipe wastes buffer space and can split segments.
  - **[I]** Protobuf can compute exact sizes cheaply, as Google.Protobuf's `CalculateSize` does. The 5-byte prefix can then be written first.
- **One copy of the generated code per root type.** **[V]** The author flags this as worst for gRPC ([#276](https://github.com/jamescourtney/FlatSharp/issues/276)).
  - **[I]** Generate one codec per message type and share it.
- **`Channel<T>` adapters around streams.** **[V]** These are FlatSharp's generated client interface.
  - **[I]** They add a queue operation per message.
- **Copying every received message with `PayloadAsNewBuffer`.** **[V]** grpc-dotnet's own doc comment warns about the copy and the large-object-heap risk.
- **Wrapping `Memory<T>` in a heap object for each buffer.** **[V]** FlatSharp does this to keep its buffer structs small.
  - **[I]** It costs an allocation per parse. A `ref struct` reader over a span avoids both the copying and the allocation.

## Applicability to GRPC.NET

These points map the findings onto [CALL-INTERFACE.md](../../CALL-INTERFACE.md). Every item here is an inference **[I]** unless marked otherwise.

### Unary fast path

The draft signature is `Process(in CallHead, ReadOnlySpan<byte> requestBody, IBufferWriter<byte> responseBody)`.

- **The span input fits.** It has the shape FlatSharp's fastest path takes: `ArrayInputBuffer` and contiguous spans, with no sequence handling. FlatSharp's evidence ([#380](https://github.com/jamescourtney/FlatSharp/issues/380)) supports the draft's choice to have the host hand the core one complete, contiguous request body, copying into a pooled array only when the body spans segments.
- **Greedy decoding avoids the lifetime problem, for most methods.** For a synchronous unary method `Reply Add(Request r)`, the request must be fully decoded before the span goes away, because the span belongs to the host. FlatSharp's Greedy mode is the model. A Lazy view would be safe only if:
  - the method is synchronous;
  - the request object cannot escape the call;
  - the host does not recycle the buffer until `Process` returns.

  The core cannot verify the second point for an arbitrary user method. A Lazy request is therefore only safe as an explicit opt-in, for example a `ref struct` request view that the compiler stops from escaping.
- **Value-type messages for small requests.**
  - FlatSharp's value structs show where allocation-free decoding works: fixed-layout value types parsed eagerly.
  - Generated protobuf messages that are `struct`s, or `ref struct`s for request-only use, would let a synchronous unary call decode with no allocation, provided they have no strings or repeated fields.
  - Strings are the limit FlatSharp's author names. A UTF-8 `ReadOnlySpan<byte>` accessor, or a `string` created only when asked for, is the only way around it.
- **The writer side.**
  - FlatSharp shows that writing straight into `IBufferWriter<byte>.GetSpan(n)` allocates nothing.
  - Protobuf can compute the exact size first: the core writes the 5-byte prefix, then the message, into the same span with one `Advance`. This is better than FlatSharp's worst-case `GetMaxSize` reservation.
  - The size pass is not free; FlatSharp's own `GetMaxSize` costs about 11% of its write time. Exact sizing should be cached per message, or fused with the write.

### Streaming path

The draft signature is `ProcessAsync(CallHead, PipeReader, PipeWriter, ICallEvents)`.

- **Contiguous messages.** The core's 5-byte framing gives each message's length before its bytes arrive. The typed reader can wait until the whole message is buffered, then decode it from one contiguous span. If the message crosses segments, it can copy into a pooled array first. This is FlatSharp's recommended approach, with no per-message allocation as `PayloadAsNewBuffer` would need.
- **Pipe advancement decides object lifetime.**
  - With greedy decoding, the reader may call `AdvanceTo` past a message as soon as it is decoded.
  - A lazy or view-style message would pin the pipe segment until user code drops it, which a `PipeReader` cannot express safely.
  - Streaming messages handed to user code should therefore be greedy and owned by the user. View types should exist only inside a single callback.
- **Typed reader and writer, not channels.** FlatSharp's channel-based client interface is a counter-example to the draft's "no `System.Threading.Channels` on the hot path". Its server side keeps grpc-dotnet's `IAsyncStreamReader<T>` and `IServerStreamWriter<T>` shapes, which match the method view the draft proposes.
- **Echo and proxy.** A method that forwards a request message unchanged could write the received bytes straight to the response pipe, like FlatSharp's memory-copy serialization. The core would need an opt-in "raw message" parameter type.

### Message lifetime over pooled pipe buffers

These are proposed rules, modelled on FlatSharp's documented contract but enforced by types where FlatSharp relies on documentation:

1. **Owned messages.** A message object given to a user method owns all its data and never refers to pipe memory. This is the default, like Greedy.
2. **Borrowed views.** A borrowed view of a message is a `ref struct`, or is valid only until the callback returns. The C# compiler, not documentation, prevents escape. FlatSharp's equivalent, Lazy mode, is undefined behaviour after buffer reuse, and nothing in its API prevents that.
3. **Raw payloads.** `ReadOnlyMemory<byte>` fields that alias the request buffer, like FlatSharp's `Memory<byte>` vectors, are offered only together with an explicit ownership transfer. For example, the host hands the core a rented array, and the message returns it when disposed. Otherwise they are copied.
4. **No pooling of message objects.** The core does not pool message objects, following FlatSharp's removal of pooling. Byte buffers are pooled; objects are not.

### Serialization: a built-in Protocol Buffers codec or Google.Protobuf

Facts that bear on the question:

- **[V] FlatBuffers itself is ruled out.** It is not wire-compatible with protobuf, so FlatSharp does not answer the question directly. GRPC.NET must interoperate with standard gRPC clients, which in practice means protobuf messages.
- **[V] FlatSharp's speed came from a built-in, generated codec.** It is generated at build time against its own buffer abstractions, with no reflection and safe span code, and it outran Google's own C# FlatBuffers library by 1.4× (parse and traverse) to 3.5× (serialize) in its benchmarks (README table). The cause is the code generation and the buffer design, not the format alone.
- **[V] The marshaller boundary forces copies.** Under the grpc-dotnet marshaller contract, FlatSharp still pays one copy per received message. A codec embedded in GRPC.NET's own core, as GRPC.NET plans, sits below the marshaller and can avoid that copy.

Inferences:

- **What a built-in codec would buy.** It would allow:
  - decoding from `ReadOnlySpan<byte>` and encoding into `IBufferWriter<byte>` with exact sizing;
  - struct and `ref struct` message shapes, and UTF-8 string accessors;
  - generation from C# attributes, which fits the JSON-RPC.NET model;
  - full control of AOT safety.

  This mirrors how jsmn replaced a JSON library in JSON-RPC.NET.
- **The cost of a built-in codec.** It must reproduce protobuf's wire rules exactly: unknown-field preservation, packed and unpacked repeated fields, proto3 presence, maps and oneofs. FlatSharp spends heavily on conformance (oracle tests against the reference library, fuzzing, mutation testing). A GRPC.NET codec would need the equivalent: round-trip tests against Google.Protobuf output, plus gRPC's interop suite.
- **Google.Protobuf as a fallback.** Google.Protobuf already offers span and `IBufferWriter` paths (`IBufferMessage`, `CalculateSize`). It could serve as a pluggable codec behind the same core interface, at the cost of its class-based, fully materialized messages.
- **A staged plan.** It follows the README's rule that every dependency must justify itself:
  1. Define a codec interface in the core: span in, buffer writer out, with exact size.
  2. Ship a Google.Protobuf adapter first, for interop.
  3. Add a built-in generated codec only if benchmarks of the unary fast path show the allocation and copy savings that FlatSharp's results suggest are available.
